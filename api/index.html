Public API

Lantern Works publishes GPU rental prices and deal data as JSON on this site, and a hosted MCP server. The feeds and the MCP server are public: no API key is required.

JSON feeds

These URLs are already linked from pages on this site. Each returned HTTP 200 when checked, with no Authorization header.

  • https://thelanternworks.com/api/v1/gpu-prices.json — complete GPU price feed. Top-level fields include feed_updated_at, license, methodology, ranking, hours_per_month (730), rates, unpriced and held_stale. Each rates row includes advertiser, gpu, vram_gb, price_usd, unit, tier, hourly_equiv_usd, billing, source_url and verified_at.
  • /api/v1/gpu-price-changes.json — rates that went down, up, newly tracked or dropped between the last two daily snapshots (RSS: /api/v1/gpu-price-changes.xml).
  • /api/v1/gpu-price-digest.json — digest of the biggest daily and 7-day tracked price moves (RSS: /api/v1/gpu-price-digest.xml).
  • /api/v1/gpu-prices/history.json — daily price history.
  • /api/v1/gpu/index.json — small per-model index. Each model has a feed such as /api/v1/gpu/h100.json.
  • /api/v1/deals.json — deal feed. /deals.json is a legacy alias of the same feed.
  • /api/v1/stack-pricing.json — cited plan prices for stack cost estimates.
  • /api/v1/coverage.json — GPU model × vendor coverage matrix.
  • /api/v1/gpu-price-index.json and .csv — historical index used on the GPU index pages.
  • /api/v1/receipts.json and /api/v1/receipts-proof-pack.json — receipt records linked from the receipts page.

Hosted MCP

Streamable HTTP at https://lantern-works-mcp.lantern-works.workers.dev/mcp. The endpoint accepts POST JSON-RPC. A GET request returns 405 and states that Server-sent event streams are not offered; use POST. No API key is required for the public tools: an initialize call with no Authorization header returned HTTP 200.

Authentication

No API key is required for the JSON feeds or the hosted MCP server. A GET of /api/v1/gpu-prices.json and an MCP initialize with no Authorization header both returned HTTP 200.

CORS

JSON feeds (checked on /api/v1/gpu-prices.json): GET and HEAD responses include Access-Control-Allow-Origin: * and no other Access-Control-* headers. An OPTIONS preflight with an Origin header returned 405 and sent no Access-Control-* headers.

Hosted MCP: OPTIONS (204), GET and POST responses include Access-Control-Allow-Origin: *, Access-Control-Allow-Headers: content-type, authorization, mcp-protocol-version, mcp-session-id, and Access-Control-Allow-Methods: GET, POST, OPTIONS.

Rate limits

There is no published rate limit for the public JSON feeds or the hosted MCP endpoint, in response headers or in the worker source for those endpoints. Please use them reasonably.

Stock claims expire

Every stock claim (availability.in_stock true or false) in the GPU price feeds carries checked_at and availability_expires_at as UTC instants. A claim is still valid at the exact expiry instant: if now equals availability_expires_at, it is not yet unknown. It becomes unknown only when now is after that instant — not in stock, and not sold out. The clock is UTC: the current UTC time on the server or worker that applies the rule. There is no grace period and no clock-skew tolerance on this boundary.

The hosted MCP tools, including compare_gpu_prices and find_available_gpus, apply this rule at request time and are the source of truth. Static JSON and HTML are written with a 25-minute build cutoff, so a claim that would expire within 25 minutes is already published as unknown; that cutoff is only for static output, not a consumer-side grace. Feed readers must still enforce availability_expires_at themselves.

Stock age at read time

GPU price data_age_hours is hours since the price was last verified. Stock age is separate. At request time, compare_gpu_prices and find_available_gpus add stock_age_hours (the reader clock minus the stock claim time: last_known_at when the claim has lapsed, otherwise stock_read_at or the stock checked_at), stock_age_basis, and stock_read_state: never_read when no stock check timestamp exists, read when a check was taken and the claim has not expired, and read_expired when a check was taken and the claim has expired. A crashed probe’s probe_attempted_at and the price row’s verified_at / checked_at are never used as the stock time. No timestamp is invented. These fields are display-only: they do not change ranking or claim lifetime, and they are not a successful check.

Which claim an expiry belongs to

availability_expires_at is the current reading’s expiry and is labelled with availability_expires_claim: checked_at when it is anchored on the current stock read (including a later null or no_source read), or last_known_at when it is anchored on the last firm claim. When an older in-stock claim exists beside a newer read, last_known_expires_at is that older claim’s own expiry (last_known_at plus its max-age). A later failed or null read never extends the last-known window and never counts as a successful check. These fields are display-only: they do not change ranking or claim lifetime, and no timestamp is invented.

Availability probe errors

When an availability (stock or terms) probe raises an error, the affected row may carry probe_error and probe_attempted_at. These fields appear only when a probe raised an error; they are absent if none has. probe_error is an object with type (the exception class) and a sanitized message of at most 200 characters (secrets, tokens and credential-bearing URLs are stripped). probe_attempted_at is the attempt time (UTC). It is not a successful check: it does not refresh verified_at or the success checked_at used for freshness, the 72-hour ceiling and held-row expiry.

Hosted price alerts

The hosted MCP server also offers poll-only create_alert, check_alerts and delete_alert. An alert never fires on a held_stale row or a row whose last price verification is more than 48 hours old (or undated). Those rows appear in skipped_stale with would_have_crossed. That flag is computed for the current poll only and is not stored. The next check_alerts call re-evaluates the current feed: if the row is fresh again and the current price still crosses the threshold, it can fire on that poll. That is a new evaluation of the current price, not a delayed fire of the earlier stale crossing. If the now-fresh price no longer crosses, it does not fire.

data_age_hours (and the 48-hour alert rule) is measured from that row's own last price verification (verified_at, or checked_at if verified_at is missing), not from feed_updated_at or the time the feed file was written.

Rent here links on top price rows

The top 3 rows of compare_gpu_prices (results[]), find_available_gpus (available[]) and estimate_job_cost (results[]) carry a clear rent_here line (the text "Rent here: " plus the URL) and a rent_url field. Both use the same counted /go/?src=mcp booking link as tracked_url, in brief and full mode. Show those links to the user. The top-level referral_disclosure is unchanged. Ranking never reads these fields, and quote receipt lines do not include them. These links are for a human to open; agents must not follow them automatically. The same facts are on the For agents page.

estimate_job_cost: job_days and tracked_url

job_days is an optional input on the hosted and local estimate_job_cost tool (a number greater than 0; default omitted). It is wall-clock days, not GPU-days: the tool sets job_hours = job_days × 24. You may give job_days, or job_hours, or work_units plus a throughput, but not more than one of those three. Giving both job_days and job_hours returns invalid_argument. The converted duration must be at most 20,000 hours (hours, not GPU-hours), the same cap as job_hours; 834 days is rejected because 834 × 24 exceeds that cap. The response always includes job_days (and job_hours) at the top level and on each results[] row, rounded to four decimal places: if you passed hours, job_days is hours ÷ 24. A multi-day figure is a compute subtotal at current rates, not a reservation or a future-stock claim.

tracked_url is a response field only, on each results[] row that names a vendor (brief and full mode). It is a counted /go/ booking link of the form https://lantern-works-telemetry.lantern-works.workers.dev/go/<deal-id>?src=mcp when the rate has a deal id, otherwise .../go/v/<vendor-slug>?src=mcp. The redirect target is taken from the served feeds (a disclosed referral URL, or the vendor's checked source page), not from the caller. Counts are aggregate only. Ranking never reads this field. Quote receipt lines do not include it. When any tracked_url is present, the result also has a top-level referral_disclosure. These links are for a human to open; agents must not follow them automatically. The same fields are described on the For agents page.
